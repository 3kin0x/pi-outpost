## Context

See `proposal.md` for motivation and `specs/web-app-installation/spec.md` for the observable contract.

Three pieces of the current implementation shape this:

- `web/index.html` is a bare Vite entry: a title, a viewport, a root div. There is no manifest link, no theme colour, no service worker anywhere in the repository.
- `web/public/` holds `favicon.svg` and `icons.svg` (an interface sprite, not app icons). Vite copies `public/` into `dist/` verbatim, so anything placed there is served at the root path.
- The interface is served two ways. `fastifyStatic` from the first `web/dist` it finds, for development and npm installs; or, when `EMBEDDED_WEB` is non-empty, from a map of base64 assets inlined at build time by `cli/scripts/embed-web.mjs`. That script assigns each asset a content type from a fixed extension table, and anything not in the table is served as `application/octet-stream`.

The requester confirmed the interface is installed from `http://127.0.0.1:PORT`. Browsers treat that as a secure context, so nothing here depends on TLS. A LAN deployment over plain HTTP is not a secure context and is out of scope.

## Goals / Non-Goals

**Goals:**

- Installable in Edge from the address bar, with no change to how the interface is served.
- Installable identically from the standalone executable, where there is no `web/` directory at all.
- An installed window that is the interface, not a subset of it.

**Non-Goals:**

- Offline capability of any kind, and therefore no service worker.
- TLS, or installation from a non-secure origin.
- The automatic install prompt on Chrome, which still requires a service worker with a fetch handler.
- Carrying a deployment's `branding.title` into the installed app's name.
- Push notifications, badging, share targets, file handlers, or any other manifest-declared OS integration.

## Decisions

### No service worker

Edge's own documentation is explicit that a service worker is not required to install a PWA, and Chrome removed the requirement for installation from its menu (mobile 108+, desktop 112+). What a service worker would buy here is the shell loading without the network — and this interface is a WebSocket client whose every screen comes from the server, so a cached shell reaches a disconnected state and stops.

Against that: a service worker is a cache that outlives the page, and the product ships an update mechanism. A stale shell served after an update is a failure mode that is hard to diagnose and easy to create, and it would be introduced to buy a marginally nicer disconnected screen.

The cost is Chrome's automatic install prompt, which still wants a fetch handler. Installation from the menu remains, and Edge — the browser the requester named — offers it in the address bar regardless.

Alternative considered: a no-op fetch handler purely to satisfy Chrome's prompt criteria. Rejected — Chrome already ignores empty handlers, and it would mean shipping a cache to trick a heuristic.

### A static manifest, carrying the product's identity, not the deployment's

The manifest is a file in `web/public/`, built into `dist/` and inlined into the executable like every other asset.

The alternative is a manifest generated by the server from `branding`, so a white-labelled deployment installs an app under its own name. That is rejected for now, for a reason that is not merely effort: a browser fetches the manifest before the interface has authenticated, and `/branding` is token-gated precisely so a token-protected server does not disclose its deployment's identity to an unauthenticated caller. A branding-derived manifest would either have to be served unauthenticated — undoing that — or fail to load on exactly the deployments that customise branding most.

A branding-aware manifest is therefore a separate change, and one that has to answer that question first.

### Icons as PNGs checked in beside the SVG

`favicon.svg` stays what it is. Installation needs raster icons at the sizes platforms present an installed app at, plus one declared `purpose: "maskable"` with its artwork inside the safe zone, so a platform that crops to a circle or a squircle does not cut into it.

They are generated once from the existing artwork and committed, rather than produced by a build step: the build already has four stages before the bench can run, and an icon set that changes only when the artwork changes does not earn a fifth.

### Teach the inlining script the manifest's content type

`cli/scripts/embed-web.mjs` maps extensions to content types and falls back to `application/octet-stream`. A manifest served as an opaque stream is ignored by the browser, so an executable build would serve a page that links a manifest the browser refuses to read — installable from `web/dist`, silently not installable from the executable.

Whichever filename the manifest takes, its extension must be in that table. This is the one place where "it works in development" and "it works in the shipped artefact" come apart, which is why the spec makes the content type an observable requirement rather than an implementation detail.

### The widget links nothing

The manifest link lives in `web/index.html`, which is the standalone interface's own document. The embed builds its own bundle and mounts into a host page's element; it never owns that page's `<head>`. Nothing needs adding to keep the widget quiet — but the spec says so anyway, because it is the kind of thing a later "just add the manifest to the embed too" would break.

## Risks / Trade-offs

- [No automatic install prompt on Chrome] → Installation from the menu still works, and Edge — the named target — offers it in the address bar. Revisit only if the prompt is actually wanted, and then weigh the stale-cache risk again.
- [An installed window pins `start_url`, so a user who installed against one server keeps opening that one] → The interface already reaches its server from the origin it was served by; the installed app behaves the same. A user running several deployments installs several apps, which is what they would want.
- [A maskable icon whose artwork sits outside the safe zone is cropped into on some platforms and looks broken only there] → Check the maskable icon in the running app on the platform, not only in the manifest, before calling it done.
- [The executable path is the one that silently loses the manifest] → Covered by a scenario rather than left to review, and it must be exercised against a real built executable rather than a mock of one.
